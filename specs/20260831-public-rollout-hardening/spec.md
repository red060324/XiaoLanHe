# 公网发布滥用防护 Spec

- Status: `DRAFT`
- Owner: red060324
- Source: active mature-platform goal and the residual rollout risks in
  `../20260831-mature-game-platform/report.md`
- Branch: `codex/clean-architecture-refactor`
- Mode: `FULL`

This spec supersedes only the abuse-protection portion of T18 in the mature
platform spec. Real payment, refund, tax, and transactional Agent tools remain
separate follow-ups. T16-T17 remain rollout tasks.

## Goal

Make the current single-instance public deployment resistant to routine login
guessing, write spam, and unbounded model/search cost without adding Java,
Redis, a queue, a second service, or private infrastructure.

## Decisions

1. Add one process-local, concurrency-safe token-bucket guard at the HTTP
   boundary using the public `golang.org/x/time/rate` package.
2. Enforce both a scope-wide backstop and a caller key where a trusted business
   key exists. Do not treat `X-Forwarded-For` or another proxy header as a
   trusted identity.
3. Use normalized username for auth, validated conversation session ID for
   Assistant chat, and authenticated user ID for writes. Hash keys before they
   enter limiter memory; never log them.
4. Protect three scopes with reviewed defaults:
   - auth: 5 requests/minute per identity, 100/minute process-wide;
   - expensive read: 6/minute per session when available, 60/minute
     process-wide, maximum 4 concurrent provider-backed requests;
   - authenticated write: 30/minute per user, 300/minute process-wide.
5. Keep the key cache at or below 10,000 entries and evict keys idle for 15
   minutes without a cleanup goroutine. When the cache is full, the global
   backstop still applies and no new per-key state is allocated.
6. Return the existing JSON error envelope with HTTP 429 and `Retry-After`.
   Rejected requests must not reach a UseCase, database, model, or search
   provider.
7. Allow an empty chat session ID so the server can create one; otherwise
   require the canonical UUID shape already generated by the server. Invalid
   IDs return 400 before storage access.
8. Keep provider billing/spending limits as a rollout control. Application
   rate limiting does not claim to replace provider-side cost caps or network
   DDoS protection.

## Scope

### In scope

- Registration and login throttling with generic responses.
- REST/SSE Assistant, knowledge embedding search, and direct Web Search cost
  guards plus a shared in-flight cap.
- Community/admin writes, coupon claims, order creation, and sandbox payment
  throttling by authenticated user.
- Bounded limiter memory, deterministic time, race safety, safe logs, config,
  public docs, and rollout smoke.
- Chat session ID boundary validation.

### Non-goals

- No CAPTCHA, MFA, account recovery, permanent account lock, IP reputation,
  browser fingerprinting, WAF, Redis, PostgreSQL rate table, or distributed
  quota service.
- No rate limiting of already bounded catalog/community/deal reads in this
  slice.
- No real payment or transactional Agent capability.
- No promise that process-local per-key quotas remain global after horizontal
  scaling. Scaling past one instance requires T9.

## Current-State Evidence

- Reusable: every mutation already passes a trusted Principal through the
  authentication middleware; responses share `httpx.WriteError`; request IDs
  are validated centrally.
- Reusable: request bodies and page sizes are already bounded, Assistant/model
  calls carry cancellation and deadlines, and coupon/order writes are
  idempotent.
- Migration debt: no endpoint has rate or concurrency admission control;
  Assistant and search can consume paid/provider resources anonymously.
- Defect: `presenter.ChatRequest.Input` validates message text but accepts an
  arbitrary `sessionId`, while PostgreSQL stores it in `varchar(64)`.
- Unsafe precedent: Hertz v0.10.6 `ClientIP()` trusts forwarded headers from
  all CIDRs by default. This spec deliberately does not use it as an abuse key.

## Acceptance Criteria

- AC1: Auth, expensive-read, and authenticated-write operations enforce the
  approved per-key and process-wide token-bucket policies before expensive or
  mutating work.
- AC2: Limiter memory remains bounded under rotating keys; concurrent access is
  race-free; disabled or invalid limits cannot silently expose a public
  deployment.
- AC3: A rejected request returns HTTP 429, the standard error envelope,
  request ID, and integer `Retry-After`; downstream call counts remain zero.
- AC4: Empty chat session IDs still create a server ID; non-empty IDs outside
  the canonical UUID shape return HTTP 400 without database/model work.
- AC5: Keys derive only from normalized username, validated session ID, trusted
  Principal, or the process-global scope. Raw credentials, cookies, messages,
  session IDs, usernames, and proxy headers never enter logs.
- AC6: Limit and concurrency settings have positive bounded defaults, strict
  parsing, `.env.example` coverage, and public deployment documentation.
- AC7: Existing successful/idempotent flows remain compatible below the limit;
  REST and SSE release in-flight permits on success, failure, and disconnect.
- AC8: Go tests, race tests, frontend regression, architecture/spec gates,
  public-only scan, Java scan, container smoke, and GitHub Actions pass.

## Assumptions And Open Questions

1. The current supported deployment is one Go process. The checked-in free
   Render plan cannot scale beyond one instance, so process-local quotas match
   the current topology.
2. The default values prioritize a portfolio/public demo. They remain explicit
   config so a measured workload can tune them without code changes.
3. Anonymous Assistant fairness is best-effort because a client can rotate a
   session ID. The process-wide limit and in-flight cap are the security/cost
   boundary; requiring login is a later product choice.
